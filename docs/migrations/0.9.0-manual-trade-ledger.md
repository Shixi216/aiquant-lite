# Router 0.9.0 stage 4: manual-trade fact ledger

Stage 4 adds an append-only ledger for trades that a user reports as already completed in an
external client. It is not an order API, broker connection, account synchronizer, or broker
verification service.

## Storage

- `manual_trade_previews` stores expiring, hashed candidates and their confirmation lifecycle.
- `manual_trades` stores user-confirmed facts with
  `UNIQUE (portfolio_id, client_trade_id)`.
- `manual_trade_corrections` links an append-only `CORRECTION` or `REVERSAL` record to the
  unchanged original trade.
- `manual_trade_reviews` stores confirmation and advisory review audit records.
- `manual_positions` is not a writable table. `ManualTradeRepository` projects positions from
  the complete trade and correction history whenever they are queried.

`source` is restricted to `USER_REPORTED` and `USER_IMPORTED`. `verification_status` is always
`USER_REPORTED`; the schema contains no broker-verified or automatic-sync status.

## Two-stage confirmation

1. An authenticated HTTP or chat actor submits a candidate.
2. Router normalizes it, calculates a canonical JSON SHA-256 hash, and returns an expiring
   `confirmation_id`.
3. No `manual_trades` row exists yet.
4. The same authenticated user and channel explicitly confirm the unchanged preview.
5. Router checks identity, expiry, status, hash, and portfolio-scoped `client_trade_id`
   uniqueness inside one transaction.
6. Router appends the trade and a confirmation audit record.
7. Repeating confirmation of the same `confirmation_id` returns the original trade without
   adding another row.

Changing a preview payload invalidates its hash. A different payload requires a new
`confirmation_id`. A correction endpoint also creates a preview; it does not bypass confirmation.

## API

| Method and route | Behavior |
|---|---|
| `POST /v1/manual-trades/previews` | Create a normal trade preview |
| `GET /v1/manual-trades/previews/{confirmation_id}` | Read preview state |
| `POST /v1/manual-trades/previews/{confirmation_id}/confirm` | Confirm as the original authenticated actor |
| `POST /v1/manual-trades/previews/{confirmation_id}/cancel` | Cancel as the original authenticated actor |
| `GET /v1/manual-trades` | List append-only trade history |
| `GET /v1/manual-trades/{trade_id}` | Read one trade |
| `POST /v1/manual-trades/{trade_id}/corrections` | Create a correction or reversal preview |
| `GET /v1/manual-positions` | Project all manual positions |
| `GET /v1/manual-positions/{position_id}` | Read one position projection |

Mutation endpoints require `X-Authenticated-User` and `X-Authenticated-Channel` from the trusted
local gateway. Do not expose this header trust boundary to a public network without real gateway
authentication.

## Isolation

- `DecisionService` accepts only `DecisionRepository` and cannot write this ledger.
- `SimulationService` has no `ManualTradeRepository` dependency.
- `ManualTradeService` accepts `ManualTradeRepository` and may read `DecisionRepository`; it has
  no simulation dependency.
- A decision, risk review, scheduled task, or Paper Trading fill cannot confirm a preview.
- A manual trade never changes Paper Trading cash or positions, and a Paper Trading fill never
  changes a manual position projection.
